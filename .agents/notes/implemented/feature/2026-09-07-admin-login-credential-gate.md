# Agent Note: Admin email+password login is `dsh web`'s only sign-in path

Status: implemented

English | [中文](2026-09-07-admin-login-credential-gate.zh.md)

## Problem

`dsh web`'s access control was the launch-token flow: a random per-process token printed in the startup URL, exchanged once for a signed browser-session cookie ([browser token authentication](../architecture/2026-08-24-browser-token-authentication.md)). That model assumes one operator who can read the process's own stdout. It has no named credential to hand to someone else, no sign-in step for an operator who wants email+password access instead of copying a URL out of a terminal, and — because the signing secret is independent of how a session was obtained — no way to later lock a deployment down without also rotating that secret out from under every existing session.

## Decision

`dsh-client-connection` requires an admin email+password login to reach `dsh web`; there is no other way in. `requireAdminCredentials` (`src/admin-login.ts`) reads `ADMIN_EMAIL` and `ADMIN_PASSWORD` from the process environment once at plugin boot and throws — failing the plugin fiber, so the process never listens — when either is missing. The raw password is hashed once (`scrypt`, a fresh random salt) and discarded; only the derived salt/hash and a SHA-256 digest of the email are retained in memory for the process lifetime. Nothing is persisted to `.credentials.yaml` or anywhere else, and the raw password never reaches a log line.

`BrowserAuth.authorizeIndex` (`src/browser-auth.ts`) serves a self-contained, script-free HTML `<form method="POST">` (`src/login-form.ts`) for an unauthenticated `GET /`; every other unauthenticated request gets the existing plain-text 401. The form posts to an exact `POST /login` route (`packages/client/connection/src/index.ts`, `src/login-route.ts`), registered ahead of the SPA fallback seat. `verifyAdminLogin` (`src/admin-login.ts`) computes both the email digest and the password hash unconditionally and compares each with `timingSafeEqual` before ANDing the results, so a wrong email costs exactly as much CPU time as a wrong password — no user enumeration, no timing side-channel. A correct submission mints the same signed, authority-bound session cookie the removed token exchange used to mint (`BrowserAuth.mintCookie`); a wrong one re-serves the form with a generic "Invalid email or password." notice. `src/login-throttle.ts` applies a fixed per-source-IP exponential backoff (500ms doubling, capped at 30s, capped tracked-key count) to failed attempts ahead of running any `scrypt` comparison — the curve is a security invariant, not a `Config` field, so an operator cannot weaken it. `authenticatedUrl` prints the bare root URL, since the credential is the email/password the operator already holds, never something carried in a link.

The persistent session-cookie mechanics — the signed, authority-bound `HttpOnly`/`SameSite=Strict` cookie, the owner-scoped `client-connection/browser-session` HMAC secret persisted via `@deepseek-ai/dsh-credentials`, and "delete the record and restart to revoke every session" as the global revocation mechanism — are unchanged from the superseded token flow; only the credential that mints the cookie changed.

## Alternatives considered

**Keep admin login opt-in alongside the launch-token flow (both credential paths available, selected by whether `ADMIN_EMAIL`/`ADMIN_PASSWORD` are set).** Built first, then reverted: dual paths share one signing secret, so a browser session obtained under one path stayed valid after switching the process into the other — an operator locking a deployment behind a login would find a stale, token-obtained browser tab still working. Closing that gap meant stamping a mode discriminator into the cookie and rejecting a mismatch, adding real complexity to defend a launch-token path this system does not otherwise want. Removing the token flow entirely removes both the complexity and the gap: there is only one credential, so there is nothing for a cookie's mode to disagree with.

**Add a full multi-user account system (signup, password reset, roles).** No requirement calls for more than one admin identity; this codebase has no user database anywhere, and building one for a single hardcoded operator would be unused surface area from day one.

**Persist the admin password (hashed) via `@deepseek-ai/dsh-credentials`, the way the browser-session HMAC secret is persisted today.** Rejected for this iteration: the literal `ADMIN_EMAIL=... ADMIN_PASSWORD=...` shape the feature was requested in implies supplying the credential fresh on every launch, and skipping persistence means there is nothing password-shaped sitting on disk to protect or rotate. Persistence remains a natural, backward-compatible follow-up if an operator wants the credential to survive without re-exporting the env vars.

**Render the login page with client-side JavaScript (fetch-based submission, inline validation).** A plain `<form method="POST">` needs no script, no CORS handling, and no client/server validation drift, and it is consistent with the constraint that the SPA/plugin graph must never load before authentication succeeds — a script-free page cannot itself become an early foothold for that graph.

**Skip attempt throttling.** The gate can be reached over a LAN if an operator later binds `--host 0.0.0.0`; an unthrottled login accepting an `ADMIN_PASSWORD` string would otherwise be a straightforward guessing target. A fixed, non-configurable exponential backoff bounds guess rate without adding operational knobs.

## Consequences

`dsh web` no longer boots without `ADMIN_EMAIL` and `ADMIN_PASSWORD` both set — a deliberate, deployment-visible breaking change from the prior always-anonymous-launch-token behavior; every launch script and CI harness that starts `dsh web` must supply both. The credential is process-lifetime-only: restarting without re-exporting both variables now fails the boot outright (fail-closed), rather than falling back to some other access path. The server still provides no TLS of its own, so the credential and session cookie remain cleartext-on-the-wire outside loopback; this feature does not change that boundary and the README says so explicitly. The in-memory `LoginThrottle` is single-process and unauthenticated by source IP alone, so it slows guessing from one source but does not defend a distributed flood — an accepted trade-off for a single-process, no-external-dependency mitigation.

## Testing

Unit coverage (`tests/admin-login.host.spec.ts`, `tests/login-throttle.spec.ts`, `tests/login-route.host.spec.ts`, `tests/browser-auth.host.spec.ts`) pins: `requireAdminCredentials` throws whenever either variable is missing (including neither set) and never returns a "disabled" state; fresh salt/hash per read; constant-time accept/reject for right/wrong email and password; the backoff schedule and its cap; per-key isolation; tracked-key eviction; every `/login` HTTP outcome (405, 429, 413 for both a declared and an actual over-cap body, 401 for a bad or wrong submission, 303 with a cookie on success); that `authorizeIndex` always serves the login page for an unauthenticated `GET /` and 401s everything else; and that `authenticatedUrl` carries no credential. `tests/node-half.host.spec.ts` pins the same behavior through `apply()`'s real route registration, including the boot-time throw and a full `/login` round trip via the registered route. `apps/cli/tests/web-auth.e2e.ts` spawns the real `dsh web` CLI: one case proves it refuses to boot without both env vars; another exercises the full HTTP flow (login form served, wrong-password rejection, throttling, successful login, an authenticated `/api` call); a third proves a forged loopback `Host` is still rejected and that a session obtained through `/login` survives a process restart on the same `$DSH_HOME`.
